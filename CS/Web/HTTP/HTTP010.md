  - 이러한 경우에 사용되는 기술을 리다이렉션이라는 용어로 지칭하며, 리다이렉션은 메시지가 프록시나 캐시 등의 특정 웹 서버 중 어디에서 끝날지 판별한다.
- 대표적인 리다이렉션 기법들은 크게 다음과 같이 구분해볼 수 있다.
  1. HTTP 리다이렉션
  2. DNS 리다이렉션
  3. 임의 캐스트 라우팅
  4. 정책 라우팅

### 현대 웹에서 필수적인 리다이렉션
- HTTP 애플리케이션은 신뢰할 수 있는 HTTP 트랜잭션이 적은 지연과 낮은 대역폭 위에서 동작하기를 기대하므로, 현대 웹에서 리다이렉션은 필수적이다.
  - 예를 들어, 웹 컨텐츠들은 한 곳에서 조회에 실패한 경우 다른 장소에서 대응할 수 있도록 여러 장소에 배포된다.
  - 또한, 클라이언트와 물리적으로 가까이에 위치한 리소스에 접근할 수 있어 응답 시간도 줄어들며, 목적지 서버가 분산되어 네트워크 혼잡도도 낮출 수 있다.
- 이렇듯 리다이렉션은 최적의 분산 컨텐츠를 조회하기 위한 기법의 총집합으로 이해할 수 있으며, 이를 위해서는 부하 균형의 과제가 포함된다.
  - 이는 두 개념이 공존하기 때문으로, 대부분의 리다이렉션 기법은 일종의 부하 균형을 포함한다.

### 기반 인프라에 따른 리다이렉션 방식
- 리다이렉션의 목표는 HTTP 메시지를 가용한 웹 서버로 최대한 빨리 전송하는 것이며, 이 과정은 다음과 같이 기반 인프라에 영향을 받는다.
  1. 브라우저 사용자는 브라우저가 클라이언트 메시지를 프록시로 전송하도록 설정할 수 있다.
  2. DNS 리졸버는 메시지 주소를 지정할 때 사용할 IP 주소를 선택한다.

  4. 웹 서버는 HTTP 리다이렉트를 활용하여 요청을 다른 웹 서버로 유도할 수 있다.
- 이렇듯 브라우저는 다른 기법과 달리 프록시로 향하는 리다이렉트 설정만이 가능함에 주의해야 한다.

## 2026-08-28 Fri
### HTTP 리다이렉션이란?
- 웹 서버들은 요청을 다른 곳으로 전송할 것을 권장하는 짧은 메시지를 클라이언트에게 반환할 수 있으며, 이를 통해 부하를 분산하기도 한다.
  - 에를 들어, 리다이렉팅 서버는 가장 부하가 적은 서버를 찾아 클라이언트의 요청을 리다이렉트할 수 있다.
  - 반면, 광범위하게 분산된 서버의 경우 서버 부하 뿐만 아니라 물리적인 거리로 인한 지연까지 염두에 두어야하기에 이러한 결정은 어려워질 수 있다.
- 다른 기법에 비해 HTTP 리다이렉션이 갖는 이점은 서버가 클라이언트의 IP 주소를 알고 있다는 점으로, 이를 통해 정보에 근거한 판단을 내릴 수 있게 된다.
- 이렇듯 서버로 향하는 요청을 변경할 수 있다는 장점에도 불구하고, HTTP 리다이렉션은 다음과 같은 단점을 수반한다.
  1. 최선의 리다이렉트를 결정하기 위해 원 서버 연산량은 늘어날 수 있다.
  2. 임의의 컨텐츠에 접근하는 과정에서 두 번의 네트워크 왕복이 필요하므로, 사용자 경험이 나빠질 수 있다.
  3. 리다이렉트 서버를 두는 경우, 해당 서버의 장애가 전체 장애로 이어질 수 있다.
- 이러한 HTTP 리다이렉션 기법의 장단점으로 인해, 해당 기법은 단독이 아닌 다른 기법과 조합되어 사용되는 경우가 많다.

## 2026-08-29 Sat
### DNS 기반 리다이렉션이란?
- 클라이언트가 임의의 웹 서버에 접근하는 경우 도메인 이름이 IP 주소로 해석되는 DNS가 필수적이며, 이는 클라이언트 OS 또는 원격 DNS 서버에 의해 처리된다.
- 덧붙여, DNS는 단일 도메인에 대해 여러 IP 주소가 결합되는 것을 허용하며 이 경우 다양한 기법에 의해 반환될 IP 주소가 결정된다.
- 대표적인 기법은 가장 흔하면서도 단순한 방식인 라운드 로빈으로, 서버의 상태나 물리적인 거리를 고려하지 않고 주소를 순환시킨다.
  - 이는 대부분의 DNS 클라이언트가 다중 주소 집합의 첫 번쨰 주소를 사용하는 점을 이용하며, 매 요청 시마다 순환된 주소를 반환하여 첫 번째 주소를 바꾼다.
  - 그러나 이러한 방식은 기본적으로 완벽하지 않으며, 대표적인 원인으로는 DNS 해석의 결과가 기억되어 재사용되는 캐싱이 있다.

## 2026-08-30 Sun
### 다양한 DNS 기반의 리다이렉션 알고리즘
- 상술했듯 DNS 기반 리다이렉션은 매 요청마다 주소를 순환하지만, DNS 서버에 따라서는 다음과 같은 향상된 결정 기법을 사용한다.
  1. 부하 균형 알고리즘: DNS 서버가 웹 서버의 부하 정도를 추적하여 가장 한가한 서버를 목록의 맨 위에 두도록 동작할 수 있다.
  2. 근접 라우팅 알고리즘: 웹 서버가 지리적으로 분산된 경우, DNS 서버는 사용자와 가장 가까운 서버를 목록의 맨 위에 두도록 동작할 수 있다.
  3. 결함 마스킹 알고리즘: DNS 서버가 네트워크의 상태를 지속적으로 모니터링하고, 정전이나 여러 네트워크 장애를 피하도록 라우팅할 수 있다.
- 이 때, 일반적으로 이러한 복잡한 서버 추적 알고리즘을 실행하는 것은 권위 있는 서버(`Authoritative Server`)라는 용어로 지칭할 수 있다.
  - 반면, 권위 있는 서버를 사용하는 방식은 클라이언트의 IP 주소가 아닌 로컬 DNS 서버의 IP 주소를 기반으로 동작한다는 한계가 있다.

## 2026-09-01 Tue
### 아이피 맥 포워딩이란?
- 이더넷 네트워크 상에서 HTTP 메시지는 주소가 포함된 패킷의 형태로 전송되며, 각 패킷은 IP 주소와 포트 번호 등을 포함한다.
  - 이 때, IP 주소와 포트 번호 등의 조합은 L4 장비가 처리할 수 있다.
  - 반면, L2 장비는 MAC 주소를 기반으로 포워딩할 수 있다.
- L4 스위치 등의 L4 장비는 L4 주소를 검사하여 이에 근거한 라우팅이 가능하며, 실제로도 여러 프록시 캐시로 라우팅하여 부하 균형을 유지할 수 있다.

## 2026-09-02 Wed
### IP 주소 포워딩이란?
- NAT라고도 불리우는 IP 주소 포워딩은 패킷을 목적지의 맥 주소가 아닌 IP 주소에 따라 라우팅한다는 점에서 차이를 보인다.
  - 맥 주소의 경우 한 홉 거리에서만 통용되는 주소체계라는 점에서 IP 주소 포워딩은 더 큰 이점을 갖는다.
- 그러나 클라이언트로부터 요청된 TCP 커넥션을 반드시 하나의 스위치에서 관리해야 하며, 목적지 서버나 프록시의 응답 역시 해당 스위치로 복귀되어야 한다.
  - 이는 라우팅 대칭성이라는 용어로 지칭되며, IP 주소 포워딩에 수반되는 문제이기도 하다.
- 이를 위해 응답의 경로를 제어할 수 있도록 패킷의 출발지 IP 주소를 스위치의 IP 주소로 바꾸는 NAT 방식을 고려해볼 수 있다.
- 이 때, NAT는 출발지 IP 주소와 목적지 IP 주소를 모두 변환하는 Full NAT와 목적지 IP만을 변환하는 Half NAT로 구분할 수 있다.
  - Full NAT의 경우 서버의 게이트웨이 설정과 무관하게 응답은 항상 NAT 장비로 전송된다.
  - Half NAT의 경우 클라이언트의 IP 주소가 그대로 유지되지만, 서버의 응답이 반드시 NAT 장비를 거치도록 게이트웨이를 설정해야만 대칭적인 통신이 가능하다.

## 2026-09-03 Thu
### 네트워크 구성요소 제어 프로토콜이란?
- 네트워크 구성요소 제어 프로토콜을 이해하기 위해서는 다음과 같은 두 요소를 이해해야 한다.
  1. NE: 패킷을 전달하는 라우터나 스위치 등의 네트워크 구성 요소들을 지칭한다.
  2. SE: 웹 서버나 프록시 캐시 등 애플리케이션 계층의 요청을 처리하는 서버 구성 요소들을 의미한다.
- 이 때, 네트워크 구성요소 제어 프로토콜은 NE가 SE와 대화할 수 있도록 지원하는 기능 전반을 지칭한다.
- 반면, 네트워크 구성요소 제어 프로토콜은 부하 균형 기능을 명시적으로 지원하지 않으며 대신 SE가 NE에게 부하 균형 정보를 제공할 수 있도록 한다.
  - 이로 인해 SE가 적합하다고 판단한대로 NE가 부하 균형을 유지한다.

  1. 명시적인 설정
  2. 동적 설정
  3. 가로채기

  - 이 기능을 활용하는 것으로 브라우저는 모든 요청에 대해 프록시에 접근할 수 있으며, 필요에 따라서는 이미 프록시가 설정된 브라우저를 설치할 수도 있다.
- 이렇듯 명시적인 설정이 적용된 브라우저의 경우 사용이 간편하지만, 다음과 같은 단점이 수반된다는 점에 주의해야 한다.
  1. 프록시 서버가 응답하지 않더라도 대상 서버에 접근할 수 없다.
  2. 네트워크 아키텍쳐가 변경된 경우 모든 변경 사항을 사용자의 브라우저마다 적용하는 것이 어렵다.

### 프록시 자동 설정 방식
- 상술한 바와 같이 브라우저 설정 방식은 네트워크 아키텍쳐 변경에 취약하며, 이러한 단점을 해결하기 위해 브라우저에 의한 동적 설정 방식을 고려할 수 있다.
  - 이 경우, 적절한 프록시 서버에 접근하기 위해 브라우저는 자기 자신을 동적으로 설정할 수 있게 되며 이를 프록시 자동 설정 프로토콜이라는 용어로 지칭한다.
- 프록시 자동 설정 프로토콜은 대부분의 브라우저가 지원하며, 이를 사용하는 브라우저는 URL 별 프록시 서버를 PAC 파일에 저장하여 활용한다.
  - 브라우저는 해당 파일을 얻기 위해 지정된 서버에 접근하도록 설정되며, 재시작할 때마다 PAC 파일을 조회하는 방식으로 동작한다.
- 이 때, PAC 파일은 `FindProxyForUrl`이라는 이름의 함수를 정의하는 JS 파일이며 브라우저은 요청된 URL마다 해당 함수를 호출하게 된다.
  - 반환된 값은 브라우저가 어떤 프록시 서버를 통해 해당 URL을 요청할 수 있을지 명시하는 문자열이며, 프록시의 목록이거나 우회 지시일 수 있다.
  - 이 때, 우회 지시는 `DIRECT` 같은 문자열로 브라우저가 임의의 프록시 서버로 우회하여 대상 서버에 접근해야함을 의미한다.
- 프록시 자동 설정 프로토콜은 강력하며, 프록시 서버에 변경이 가해지더라도 PAC 파일이 갱신되어 이에 대응할 수 있게 된다.
  - 이러한 편리함으로 인해 프록시 자동 설정 프로토콜은 주요 ISP들에 의해 사용되기도 한다.

### 인터넷 캐시 프로토콜
- ICP라고 불리우는 인터넷 캐시 프로토콜은 캐시들이 형제 캐시에서 발생한 캐시 적중을 조회할 수 있도록 지원한다.
  - 예를 들어, 임의의 컨텐츠 요청에 대해 캐시는 형제 캐시 중 컨텐츠를 갖는 캐시를 찾는 방식으로 동작한다.
  - 형제 캐시 중 컨텐츠를 갖는 캐시가 발견된 경우, 원 서버에 질의하는 것보다 더 적은 비용으로 가져올 수 있을 것으로 예상하고 컨텐츠를 조회하게 된다.
  - 즉, ICP는 일종의 캐시 클러스터링 프로토콜에 해당한다고 이해할 수 있다.
- 한 차례 이상의 ICP 질의로 HTTP 요청 메시지의 최종 목적지를 결정할 수 있다는 측면에서 ICP는 리다이렉션 프로토콜로 취급해도 무방하다.
- ICP는 단순하고 가벼우며, 대상 캐시 뿐만 아니라 근처 캐시 모두에 대해 특정 URL에 대응하는 컨텐츠를 갖는지 질의하는 객체 발견 프로토콜이다.

### 캐시 배열 라우팅 프로토콜
- 프록시 서버는 각 클라이언트로부터의 요청을 가로채어 웹 캐시의 사본을 제공하므로 인터넷으로 향하는 트래픽을 크게 경감한다.

  - 즉, CARP라는 이름은 프록시 서버의 배열이 클라이언트 관점에서 논리적으로 하나의 캐시처럼 보이게 한다는 점에서 유래되었다.

## 2026-09-11 Fri
### ICP와 CARP 비교하기
- 상술한 두 프로토콜은 모두 여러 대의 프록시 서버를 활용하여 성능을 개선하도록 지원하는 프로토콜이지만, 세부적인 동작 방식에서 다음과 같은 차이를 갖는다.
  1. ICP: 캐시 비적중시 이웃 캐시들에게 ICP 메시지를 전달하여 질의한다.
  2. CARP: 컨텐츠 URL에 해시 함수를 적용하여, 임의의 컨텐츠를 특정 프록시 서버에 매핑하는 식으로 동작한다.
- 이렇듯 ICP는 서로 연결된 서버 간에 중복된 컨텐츠가 발생할 수 있으나, CARP는 개별 컨텐츠가 하나의 서버에만 속한다는 장점을 갖는다.
  - 이로 인해 ICP는 여러 번의 질의 메시지가 발생할 수 있으나, CARP는 한 번의 검색만으로도 컨텐츠의 위치를 결정할 수 있다.
- 반면, CARP는 프록시 서버 중 하나에 문제가 발생했을 경우 이 사실을 반영하기 위한 비용이 큰 축에 속한다.
  - 예를 들어 해시 함수를 재조정하고, 조정된 함수에 따라 컨텐츠를 재배치해야할 수 있다.
  - 그러나 ICP의 경우 이미 컨텐츠가 중복되어 존재할 수 있으므로 임의의 서버 중단으로 인핸 재배치 작업이 필요하지 않다.
- 이렇듯 여러 서버가 협력하지만 분산되는 ICP와, 서버 그룹을 하나의 캐시 집단으로 취급하는 CARP는 서로 다른 장단점을 갖는다.

### 하이퍼텍스트 캐싱 프로토콜
- HTCP라고 불리우는 하이퍼텍스트 캐싱 프로토콜은 형제들이 URL 뿐만 아니라 요청 및 응답 헤더를 통해 컨텐츠 존재 여부를 질의할 수 있도록 지원한다.
  - 이는 HTTP/0.9를 염두에 두고 설계된 ICP와의 큰 차이점에 해당한다.
  - HTTP/1.0과 1.1 버전은 URL에 더해 문서 매칭에 대한 판단을 위한 많은 요청 헤더가 도입되었으므로, ICP는 정확한 응답을 조회하지 못할 수 있다.
- 나아가 HTCP는 캐시들이 서로의 캐시 안에 있는 컨텐츠의 추가나 삭제를 모니터링하고 요청할 수 있으며, 각 캐시에 대한 캐싱 정책을 변경할 수 있도록 지원한다.
