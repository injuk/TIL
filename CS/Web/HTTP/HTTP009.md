# HTTP
## 2026-07-20 Mon
### 국제적인 컨텐츠를 지원하기 위한 HTTP 스펙
- HTTP 메시지는 컨텐츠라면 기반 언어를 불문하고 미디어처럼 실어나를 수 있으며, 이 관점에서 HTTP 엔티티 본문은 그저 비트의 연속에 불과하다.
- 반면, 국제 컨텐츠를 지원하기 위해 서버는 클라이언트가 알 수 있도록 각 문자와 언어를 명시할 수 있다.
  - 이를 통해 클라이언트는 문자를 구성하는 비트들을 올바른 방법으로 처리하여 사용자에게 컨텐츠를 제공할 수 있다.
- 이렇듯 서버가 클라이언트에게 전달하는 문자와 언어 정보는 `charset`과 Content-Language 헤더에 명시된다.
- 동시에 클라이언트는 서버에게 어떠한 언어를 이해할 수 있고, 처리할 수 있는지 명시할 필요가 있다.
  - 이 때 사용되는 헤더는 Accept-Charset과 Accept-Language이며, 각각 어떤 인코딩 알고리즘과 어떤 언어를 이해할 수 있는지 명시한다.

## 2026-07-21 Tue
### 차셋이란?
- HTTP 차셋(`charset`)은 임의의 컨텐츠 비트들을 특정한 문자 체계의 글자들로 바꾸는 방법을 의미한다.
- 각 차셋은 임의의 차셋 태그를 명시하며, 이러한 태그들은 각각 비트를 글자로 변경하거나 그 역의 작업을 수행하는 알고리즘에 대한 명명에 해당한다.
  - 이러한 차셋 태그의 목록은 표준화되어 IANA에 의해 관리된다.
- 예를 들어 `Content-Type: text/html; charset=iso-8859-6`과 같은 헤더는 컨텐츠 수신자에게 다음과 같은 정보를 제공한다.
  1. 컨텐츠는 HTML 파일이다.
  2. 컨텐츠를 구성하는 비트들은 아랍 문자집합 디코딩 기법인 `iso-8859-6`에 의해 글자로 디코딩되어야 한다.
- 상술한 `iso-8859-6`의 경우 8비트 값을 몇몇 특수문자를 포함하는 라틴 문자 또는 아랍 문자로 매핑하는 알고리즘에 해당한다.
  - 반면, UTF-8과 같은 몇몇 문자 인코딩 방식은 글자 당 비트 수가 일정하지 않기에 처리 과정이 더 복잡할 수 있다.
  - 그러나 이러한 인코딩 방식은 중국어나 일본어와 같이 절대적인 글자 수가 다른 언어에 비해 많은 문자체계를 지원할 수 있다는 장점 역시 존재한다.

## 2026-07-22 Wed
### 적절한 차셋 사용의 중요성
- 문자를 사용하기 위해서는 우선 비트들을 문자로 변환하는 디코딩 알고리즘을 지정하고, 이를 적용하는 표준화된 방법이 필요할 수 있다.
- 국제화된 문자 시스템의 목표는 시각적인 표현 방식인 표현에서 글자들 그 자체인 의미를 분리하는 것인 반면, HTTP는 문자 데이터와 차셋 전송에만 관심을 갖는다.
- 때문에 클라이언트가 잘못된 `charset` 매개변수를 사용한다면 클라이언트는 서버로부터 받은 컨텐츠를 잘못 디코딩하므로 깨진 데이터를 보여주게 된다.
  - 예를 들어, 본문이 서유럽 문자 코드 인코딩인 `iso-8859-1`로 인코딩되었지만 클라이언트가 다른 인코딩을 사용할 경우 의도와는 다른 문자가 출력된다.

## 2026-07-23 Thu
### MIME 차셋이란?
- 특정한 문자 인코딩과, 특정하게 코딩된 문자집합의 결합은 MIME 차셋이라는 용어로 지칭한다.
  - 이러한 MIME 차셋은 IANA에 의해 등록되어 관리되며, HTTP의 경우 표준화된 MIME 차셋 태그를 Content-Type과 Accept-Charset 헤더에 사용한다.
- 여러 문서와 브라우저에 의해 사용될 수 있는 MIME 차셋 인코딩 구조의 예시 중 가장 유명한 두 종류는 다음과 같다.
  1. us-ascii: ASCII라고도 불리는 유명한 문자 인코딩으로, 여러 국제 변형이 있기에 정확한 식별을 위해 `us-` 접두사를 붙인다.
  2. utf-8: 전 세계 문자들에 대한 보편적인 문자 집합인 유니코드를 표현하기 위한 가변길이 문자 인코딩 구조이다.

## 2026-07-24 Fri
### <META> 태그와 문자 집합 추론 
- 웹 서버는 클라이언트에게 MIME 차셋 태그를 `charset` 매개변수화 함께 다음과 같이 전송할 수 있다.
```text
Content-Type: text/html; charset=iso-2022-jp
```
- 만약 이러한 문자집합이 명시되지 않았다면, 수신자는 문서의 `<META>` 등과 같은 태그로부터 문자 집합을 추측하려 시도한다. 
  - 그러나 이러한 정보조차 주어지지 않았다면 언어와 인코딩에 대한 일반적인 패턴을 찾아내기 위해 텍스트를 읽어들여 문자 인코딩을 추측하는 방식으로 동작한다.
  - 반면, 클라이언트가 어떠한 정보로부터도 문자 인코딩을 추측할 수 없다면 서유럽 언어를 위한 인코딩 방식인 iso-8859-1로 가정하게 된다.

## 2026-07-25 Sat
### Accept-Charset 헤더의 사용
- 세상에는 이미 사용되고 있는 수많은 문자 인코딩 방식이 존재하는 반면, 대부분의 클라이언트는 모든 문자 인코딩 방식을 지원하지 못한다.
- 이로 인해 클라이언트는 서버에게 자신이 무엇을 지원할 수 있는지 `Accept-Charset: iso-8859-1, utf-8`과 같이 헤더에 명시할 수 있다.
  - 해당 헤더는 클라이언트가 지원하는 문자 인코딩의 목록을 의미하며, 이 구조 중 서버가 무엇을 선택할지는 전적으로 서버의 결정에 달려 있다.
- 반면, 응답 문자집합은 MIME과의 호환을 위해 Content-Type 헤더의 `charset` 매개변수로 명시된다.
  - 다시 말해, Content-Charset과 같은 대응 헤더가 존재하지 않는다는 점에 주의해야 한다.

## 2026-07-26 Sun
### 다중언어 문자 인코딩 이해의 어려움
- 국제화된 애플리케이션 또는 컨텐츠로 작업하는 개발자는 기술 명세를 이해하고, 올바른 구현을 위해 다중언어 문자집합 체계를 깊이 이해할 필요가 있다.
- 그러나 이러한 문자 체계를 배우는 것은 다음과 같은 이유에서 쉽지 않다.
  1. 용어들은 복잡하고 일관성이 없다.
  2. 때로는 임의의 표준 문서를 읽기 위해 비용을 지불해야 한다.
  3. 무엇보다, 작업 대상 언어 자체에 익숙하지 않을 수 있다.

## 2026-07-27 Mon
### 문자집합 용어 정리하기
- 다중언어 문자집합 체계를 깊이 있게 이해하기 위해서 알아두어야 할 용어를 간단히 정리하면 크게 다음과 같다.
  1. 문자: 알파벳 글자나 숫자, 표의 문자처럼 글쓰기의 최소 단위를 의미한다.
  2. 글리프: 하나의 글자를 표현하기 위해 다른 글자와 구분 가능한 시각적 형태로, 하나의 글자는 여러 글리프를 가질 수도 있다.
  3. 코딩된 문자: 글자를 다룰 수 있도록 각각의 글자에 할당된 유일한 숫자를 의미한다.
  4. 코드 공간: 문자 코드 값으로 사용하기 위해 계획된 정수의 범위에 해당한다.
  5. 코드 너비: 각 문자 코드의 비트 개수이며, 고정된 크기를 갖는다.
  6. 사용 가능 문자집합: 글자들에 대한 특정한 작업 집합으로, 세상에 존재하는 모든 글자들의 부분집합에 해당한다.
  7. 코딩된 문자집합: 사용 가능 문자집합에 대해 각 극자마다 코드 공간의 코드를 할당해주는 코딩된 문자들의 집합이다.
  8. 문자 인코딩 구조: 숫자로 표현된 문자 코드들을 컨텐츠 비트 형태로 인코딩하거나 그 역으로 디코딩하는 알고리즘을 의미한다.

## 2026-07-28 Tue
### 차셋이라는 표현의 모호함
- 엄밀히 말해 MIME 차셋 태그는 문자집합을 의미하는 것이 아니며, 차셋 값은 데이터 비트를 고유한 문자의 코드로 매핑하는 알고리즘을 지칭한다.
  - 즉, 이는 상술한 문자 인코딩 구조와 코딩된 문자집합의 개념을 합친 것에 해당한다.
- 차셋이라는 표현은 그 모호함으로 인해 혼란을 주기 쉬운데에 더해, 이미 문자 인코딩 구조와 코딩된 문자집합을 지칭하는 표준이 존재한다는 점에서 더 복잡하다.
  - 이로 인해, 표준 문서를 읽는 과정에서는 정확히 무엇이 정의된 것인지 확실히하기 위해 주의를 기울일 필요가 있다.

## 2026-07-29 Wed
### 문자와 글리프
- 문자는 쓰기의 기본적인 구성요소로, 쓰기의 기본 단위이나 글꼴이나 스타일과는 독립적이어야 한다.
- 그러나 동일한 문자가 위치나 용도에 따라 모양 또는 패턴이 크게 변경되는 경우가 있으며, 그럼에도 이들 문자는 모두 동일한 문자로 취급되어야 한다.
  - 이렇듯 동일한 문자가 위치에 따라 형태가 바뀌는 표기 체계는 생각보다 다양하다.
- 문자는 유일하고 추상화된 언어의 요소인 반면, 글리프는 각 글자를 그리는 특정한 방법이다.
  - 상술한 내용에 따라, 동일한 문자가 여러 개의 글리프에 대응될 수 있다.
  - 일반적으로, 글리프를 다른 것으로 바뀌었을 때 텍스트의 의미가 바뀐다면 두 글리프는 서로 다른 글자를 가리키는 것과 같다.

### 코딩된 문자집합이란?
- 코딩된 문자집합은 RFC로 정의되며, 정수를 글자에 대응시키는 역할을 담당한다.
  - 일반적인 코딩된 문자집합은 코드 번호로 인덱싱된 배열로 구현되며, 각 배열의 원소들은 문자가 된다.
- 역사적으로 유의미한 문자집합은 크게 다음과 같이 정리할 수 있다.
  1. US-ASCII
  2. iso-8859
  3. JIS X0201
  4. 유니코드

## 2026-07-31 Fri
### 문자 인코딩 구조란?
- 문자 인코딩 구조들은 숫자로 된 문자 코드를 컨텐츠 비트로 변환하거나, 그 역으로 문자 코드로 환원하는 역할을 담당한다.
- 이러한 문자 인코딩 구조는 크게 다음과 같은 세 분류로 나누어 생각해볼 수 있다.
  1. 고정폭: 각 코딩된 문자를 고정 길이 비트로 표현하므로 빠르지만 공간이 낭비될 수 있다.
  2. 비모달 가변폭: 다른 문자 코드 번호에 서로 다른 길이 비트를 적용하므로 자주 사용되는 글자의 비트 수를 줄일 수 있다.
  3. 모달 가변폭: 다른 모드로의 전환을 위해 특별한 이스케이프 패턴을 사용하며, 처리가 복잡하지만 그만큼 복잡한 표기 체계를 효과적으로 지원한다.

## 2026-08-01 Sat
### 문자 인코딩 구조의 예시
- 여러 문자 인코딩 구조 중 대표적인 것을 몇가지 다뤄보자면 다음과 같다.
  1. 8비트: 고정폭 아이덴티티 인코딩으로, 각 문자 코드를 이에 대응하는 8비트 값으로 인코딩한다.
  2. UTF-8: 문자 코드의 값을 위해 비모달 가변길이 인코딩을 사용하며, 아스키와 호환된다는 강점이 있다.
  3. iso-2022-jp: 일본어 인터넷 문서를 위해 사용되는 인코딩이며, 가변길이 모달 인코딩에 해당한다.
  4. euc-jp: 또 하나의 유명한 일본어 인코딩으로, 유닉스 운영체제 하에서 아시아 문자들을 지원하기 위해 제안되었다.
  5. euc-kr: 한글 인터넷 문서를 위해 널리 사용되는 가변길이 인코딩에 해당한다.

## 2026-08-02 Sun
### 언어 태그와 HTTP
- 언어 태그는 언어 자체에 이름을 붙이기 위한 짧고 표준화된 문자열을 지칭한다.
  - 예를 들어, 프랑스어 문서는 명명자에 따라 `French`나 `France` 등 다양한 단어를 고려하게 된다.
- 표준화된 언어 태그는 이러한 혼란을 방지하며, 변형된 방식이나 방언을 포함하여 각 언어에 대해 단 하나의 태그를 제공한다.
  - 대표적인 언어 태그로는 영어를 의미하는 en과 한국어를 의미하는 ko의 예시를 들 수 있다.
  - 반면, 브라질 포르투갈어를 의미하는 pr-BR과 미국 영어를 지칭하는 en-US 등 변형된 방식에 대해서도 언어 태그가 할당될 수 있다.

## 2026-08-03 Mon
### Content-Language 헤더의 사용
- Content-Language 헤더 필드는 해당 컨텐츠가 어떤 언어 사용자를 대상으로 작성되었는지 명시한다.
  - 예를 들어, `Content-Language: fr`은 프랑스어 사용자를 대상으로 작성된 컨텐츠임을 의미한다.
- 이러한 헤더는 텍스트 문서만을 위한 개념이 아니며, 오디오나 영상 및 애플리케이션 등의 컨텐츠 유형 역시 특정한 언어 사용자를 겨냥하여 제작되었을 수 있다.
- 반면, 임의의 컨텐츠가 여러 언어 사용자를 대상으로 작성되었다면 `Content-Language: mi, en`과 같이 여럿을 나열할 수 있다.
  - 그러나 여러 언어가 혼용된다고 해서 이를 모두 명시할 필요는 없으며, 예를 들어 '라틴어 첫걸음'은 오직 영어권 사용자만을 위한 컨텐츠일 수 있다.

### 이스케이핑과 역이스케이핑
- URI 이스케이프는 예약된 문자나, 공백과 같이 지원되지 않는 문자들을 URI에 안전하게 삽입할 수 있는 방법을 지원한다.
- 이스케이프는 `%<HEX><HEX>`와 같이 `%` 기호에 두 개의 16진수 글자로 구성된 세 글자 문자열로, 16진수 두 글자는 US-ASCII에 포함된 문자의 코드이다.
  - 예를 들어 URI에 공백을 삽입하는 경우, 이스케이프 결과는 `%20`이 된다.
  - URI에 사용된 글자들 중 이스케이핑된 코드 바이트들은 원래의 ASCII 코드 바이트로 변환되는 방식으로 해석된다.
- HTTP 애플리케이션은 내부적으로 데이터가 실제로 필요할 때에만 URI를 언이스케이핑해야 하며, 반드시 두 번 언이스케이핑되지 않도록 보장해야 한다.
  - 이는 언이스케이핑된 결과로 퍼센트 기호가 포함된 URI가 반환되었을 때 다시 한 번 언이스케이프되어 데이터의 손실을 유발할 수 있기 때문이다.
- 또한 이스케이프 값들은 반드시 US-ASCII 코드 범위 내에 있어야 하며, 이 규칙을 어겨 오용할 경우 애플리케이션 오류로 이어질 수 있다.
  - US-ASCII는 0부터 127까지의 자연수로 표현된 코드만을 정의하는 점에 주의해야 한다.

  4. Accept-Encoding: 인코딩 선호도를 명시하며, 서버는 Content-Encoding으로 대응한다.
- 반면, 이러한 내용 협상 헤더는 앞서 다루었던 엔티티 헤더와는 다음과 같은 차이를 갖는다는 점에 주의해야 한다.
  1. 엔티티 헤더: 일종의 메타데이터로, 서버에서 클라이언트로 응답할 때 명시하는 메시지 본문의 속성에 해당한다.
  2. 내용 협상 헤더: 클라이언트와 서버가 정보를 교환하여 적절한 버전의 문서를 선택하도록 지원하는 의사 결정 수단에 해당한다.
- 이 때, HTTP는 상태가 없는 프로토콜이기에 클라이언트는 매 요청마다 자신의 선호 정보를 명시해야 한다.
- 이러한 내용 협상 헤더 기반의 서버 주도 협상은 클라이언트 주도 협상에서 있었던 비효율적인 통신 시간을 줄여준다는 장점을 갖는다.
  - 그러나, 클라이언트의 선호 정보에 대응하는 컨텐츠가 없는 경우 서버는 적절한 컨텐츠를 추측하여 제공하는 방식으로 동작해야 한다.

### 내용 협상 헤더와 품질
- HTTP의 경우 클라이언트가 각 선호 정보마다 여러 개의 선택 가능한 항목을 선호도와 함께 나열할 수 있도록 품질값 개념을 정의하고 있다.
  - 예를 들어, `Accept-Language: en;q=1.0, fr;q=0.5, tr:q=0.0`과 같이 Accept-Language 헤더에 선호 언어 목록과 품질값을 명시할 수 있다.

  - 이에 따라, 상술한 예시는 기본적으로 영어 버전의 문서를 원하지만 상황이 여의치 않은 경우 프랑스어 문서에도 대응할 수 있음을 의미한다.
  - 그러나 터키어 버전의 경우 선호도가 0.0으로 명시되어 있으므로 원하지 않는다는 정보까지 얻어낼 수 있다.
- 서버는 클라이언트의 선호에 대응하는 문서를 단 하나도 제공하지 않는 경우도 있을 수 있으며, 이 경우 서버는 문서를 고치거나 트랜스코딩해야할 수 있다.

### Vary 헤더의 용도
- 서버가 어떤 페이지를 반환할지 판단하기 위해 헤더들을 참조하고 있다면, 캐시는 반드시 그 헤더가 무엇인지 알아야 한다.
  - 나아가 그 헤더에 대해 어떠한 논리를 적용하여 최종 결과를 선택했는지에 대한 정보 역시 알고 있어야 한다.
- 이를 위해 HTTP 응답 헤더인 Vary는 서버가 문서를 선택하거나 컨텐츠를 생성할 때 고려한 클라이언트의 요청 헤더 모두를 나열하는 데에 사용된다.
  - 예를 들어, 서버가 User-Agent 헤더에 의존한다면 Vary 헤더는 최소한 `User-Agent`를 포함해야 한다.
- 새로운 요청에 대해 캐시는 내용 협상 헤더를 활용하여 가장 적절한 것을 찾고, 이를 클라이언트에게 제공하기 전에 Vary 헤더의 포함 여부를 확인해야 한다.
  - 캐시된 응답에 서버로부터 전달된 Vary 헤더가 존재한다면, 해당 헤더의 값이 새 요청과 캐시된 요청 사이에 부합해야 한다.
  - 다시 말해, 캐시는 투명 협상을 위해서 캐시된 얼터네이트에 더해 클라이언트의 요청 헤더 및 서버의 응답 헤더를 함께 저장해야 한다.
- 캐시는 얼터네이트마다 적절한 문서 버전을 저장해야 하며, 검색 시에는 내용 협상 헤더로 컨텐츠를 추린 후 요청의 얼터네이트를 캐시된 결과와 대조해야 한다.
  - 이 과정에서 일치하는 얼터네이트가 존재하지 않는다면 서버로부터 새로운 사본을 가져올 필요가 있다.

### HTTP 리다이렉션이란?
- 웹 서버들은 요청을 다른 곳으로 전송할 것을 권장하는 짧은 메시지를 클라이언트에게 반환할 수 있으며, 이를 통해 부하를 분산하기도 한다.
  - 에를 들어, 리다이렉팅 서버는 가장 부하가 적은 서버를 찾아 클라이언트의 요청을 리다이렉트할 수 있다.
  - 반면, 광범위하게 분산된 서버의 경우 서버 부하 뿐만 아니라 물리적인 거리로 인한 지연까지 염두에 두어야하기에 이러한 결정은 어려워질 수 있다.
- 다른 기법에 비해 HTTP 리다이렉션이 갖는 이점은 서버가 클라이언트의 IP 주소를 알고 있다는 점으로, 이를 통해 정보에 근거한 판단을 내릴 수 있게 된다.
- 이렇듯 서버로 향하는 요청을 변경할 수 있다는 장점에도 불구하고, HTTP 리다이렉션은 다음과 같은 단점을 수반한다.
  1. 최선의 리다이렉트를 결정하기 위해 원 서버 연산량은 늘어날 수 있다.
  2. 임의의 컨텐츠에 접근하는 과정에서 두 번의 네트워크 왕복이 필요하므로, 사용자 경험이 나빠질 수 있다.
  3. 리다이렉트 서버를 두는 경우, 해당 서버의 장애가 전체 장애로 이어질 수 있다.
- 이러한 HTTP 리다이렉션 기법의 장단점으로 인해, 해당 기법은 단독이 아닌 다른 기법과 조합되어 사용되는 경우가 많다.

## 2026-08-29 Sat
### DNS 기반 리다이렉션이란?
- 클라이언트가 임의의 웹 서버에 접근하는 경우 도메인 이름이 IP 주소로 해석되는 DNS가 필수적이며, 이는 클라이언트 OS 또는 원격 DNS 서버에 의해 처리된다.
- 덧붙여, DNS는 단일 도메인에 대해 여러 IP 주소가 결합되는 것을 허용하며 이 경우 다양한 기법에 의해 반환될 IP 주소가 결정된다.
- 대표적인 기법은 가장 흔하면서도 단순한 방식인 라운드 로빈으로, 서버의 상태나 물리적인 거리를 고려하지 않고 주소를 순환시킨다.
  - 이는 대부분의 DNS 클라이언트가 다중 주소 집합의 첫 번쨰 주소를 사용하는 점을 이용하며, 매 요청 시마다 순환된 주소를 반환하여 첫 번째 주소를 바꾼다.
  - 그러나 이러한 방식은 기본적으로 완벽하지 않으며, 대표적인 원인으로는 DNS 해석의 결과가 기억되어 재사용되는 캐싱이 있다.

## 2026-08-30 Sun
### 다양한 DNS 기반의 리다이렉션 알고리즘
- 상술했듯 DNS 기반 리다이렉션은 매 요청마다 주소를 순환하지만, DNS 서버에 따라서는 다음과 같은 향상된 결정 기법을 사용한다.
  1. 부하 균형 알고리즘: DNS 서버가 웹 서버의 부하 정도를 추적하여 가장 한가한 서버를 목록의 맨 위에 두도록 동작할 수 있다.
  2. 근접 라우팅 알고리즘: 웹 서버가 지리적으로 분산된 경우, DNS 서버는 사용자와 가장 가까운 서버를 목록의 맨 위에 두도록 동작할 수 있다.
  3. 결함 마스킹 알고리즘: DNS 서버가 네트워크의 상태를 지속적으로 모니터링하고, 정전이나 여러 네트워크 장애를 피하도록 라우팅할 수 있다.
- 이 때, 일반적으로 이러한 복잡한 서버 추적 알고리즘을 실행하는 것은 권위 있는 서버(`Authoritative Server`)라는 용어로 지칭할 수 있다.
  - 반면, 권위 있는 서버를 사용하는 방식은 클라이언트의 IP 주소가 아닌 로컬 DNS 서버의 IP 주소를 기반으로 동작한다는 한계가 있다.

### 임의 캐스트 어드레싱이란?
- 임의 캐스트 어드레싱은 실험적인 기법으로, 멀리 떨어진 웹 서버들이 백본 라우터의 기능에 의지하여 가장 가까운 서버를 판정할 수 있다는 데에서 제안되었다.
- 그러나 이를 위해서는 웹 서버와 라우터 간에 다음과 같은 작업이 가능하다는 것이 전제되어야 한다.
  1. 웹 서버가 반드시 라우터가 이해할 수 있는 언어로 통신해야 한다.
  2. 라우터가 주소 충돌을 반드시 다룰 수 있어야 한다.

## 2026-09-01 Tue
### 아이피 맥 포워딩이란?
- 이더넷 네트워크 상에서 HTTP 메시지는 주소가 포함된 패킷의 형태로 전송되며, 각 패킷은 IP 주소와 포트 번호 등을 포함한다.
  - 이 때, IP 주소와 포트 번호 등의 조합은 L4 장비가 처리할 수 있다.
  - 반면, L2 장비는 MAC 주소를 기반으로 포워딩할 수 있다.
- L4 스위치 등의 L4 장비는 L4 주소를 검사하여 이에 근거한 라우팅이 가능하며, 실제로도 여러 프록시 캐시로 라우팅하여 부하 균형을 유지할 수 있다.

## 2026-09-02 Wed
### IP 주소 포워딩이란?
- NAT라고도 불리우는 IP 주소 포워딩은 패킷을 목적지의 맥 주소가 아닌 IP 주소에 따라 라우팅한다는 점에서 차이를 보인다.
  - 맥 주소의 경우 한 홉 거리에서만 통용되는 주소체계라는 점에서 IP 주소 포워딩은 더 큰 이점을 갖는다.
- 그러나 클라이언트로부터 요청된 TCP 커넥션을 반드시 하나의 스위치에서 관리해야 하며, 목적지 서버나 프록시의 응답 역시 해당 스위치로 복귀되어야 한다.
  - 이는 라우팅 대칭성이라는 용어로 지칭되며, IP 주소 포워딩에 수반되는 문제이기도 하다.
- 이를 위해 응답의 경로를 제어할 수 있도록 패킷의 출발지 IP 주소를 스위치의 IP 주소로 바꾸는 NAT 방식을 고려해볼 수 있다.
- 이 때, NAT는 출발지 IP 주소와 목적지 IP 주소를 모두 변환하는 Full NAT와 목적지 IP만을 변환하는 Half NAT로 구분할 수 있다.
  - Full NAT의 경우 서버의 게이트웨이 설정과 무관하게 응답은 항상 NAT 장비로 전송된다.
  - Half NAT의 경우 클라이언트의 IP 주소가 그대로 유지되지만, 서버의 응답이 반드시 NAT 장비를 거치도록 게이트웨이를 설정해야만 대칭적인 통신이 가능하다.
